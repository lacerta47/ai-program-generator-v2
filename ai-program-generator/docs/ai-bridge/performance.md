# 브리지 응답 시간 개선 방향

## 현재 근거

첫 Codex 답신은 약 170초·29,239토큰, 첫 Claude 답신은 약 160초였다. 두 질문의 작업량·모델·출력 길이·계측 범위가 같지 않아 속도 비교나 평균으로 사용하지 않는다. Claude 쪽은 현재 전체 벽시계 시간만 기록해 시작 지연·도구 실행·답변 생성 시간을 분리할 수 없다.

## 먼저 적용할 운영 방법

1. **입력 범위 줄이기:** 전체 기록 대신 쟁점, 변경 요약, 확인한 SHA, 읽을 파일을 제공한다. 이전 답신 전체와 대량 산출물의 재탐색을 요청하지 않는다.
2. **질문 묶기:** 같은 변경의 분리 기준·규칙·승인 경계를 한 리뷰로 묻는다. 상대 답신을 기다리는 동안 독립적인 백업·테스트·초안 작성을 진행한다.
3. **답변 범위 정하기:** 짧은 확인에는 글자 수와 추가 탐색 범위를 제시한다. 실패 지적·미확인 사항은 생략하지 않는다. 보안 검토에는 필요한 만큼의 탐색을 허용한다.
4. **호출 횟수 줄이기:** 상태 공유는 Issue/PR로 남기고 리뷰 1회와 필요한 부분 재검토를 기본으로 삼는다. 초마다 호출하거나 서로 무한 재호출하지 않는다.

이번 협업 규칙 리뷰에서는 위 방법을 적용하되 모델·추론 수준은 바꾸지 않는다. 측정값은 해당 편지의 소요 시간으로 남긴다. 질문 범위가 다르므로 짧아져도 통제된 성능 시험이나 일정한 단축률로 발표하지 않는다.

실제 [두 번째 검토](inbox/claude/2026-11-19-cooperation-review.md)는 지정 4파일과 짧은 답변 요청으로 95초에 수신됐다(앞선 160초보다 벽시계 기준 65초 짧음). 질문 난도·출력 길이도 달라 입력 축소만의 효과로 분리할 수 없다. Claude는 승인 출처·백업 삭제 주체·병합 전 리뷰 재등급 등의 실질적인 보완점도 제시했다. 검토를 단순 수신 확인으로 줄인 결과는 아니다.

## 후속 구현 후보와 절충

| 후보 | 기대 효과 | 판단 조건 |
|---|---|---|
| 구조화된 출력으로 토큰·모델·전체/추론/도구 소요를 가능한 범위에서 기록 | 병목을 측정한 뒤 최적화 | CLI 버전별 JSON 형식 확인, 실패 응답 처리 유지 |
| 짧은 확인용 낮은 추론 수준 또는 빠른 모델 | 일부 질문의 대기 감소 가능 | 같은 질문 묶음의 품질·시간·사용량을 비교하고 적용 범위를 결정 |
| 세션 재사용 | 반복되는 문맥 설명 감소 가능 | 현재 세션 비저장 방침과 충돌. 오래된 HEAD·문맥 혼입·동시 접근·보관 정책을 먼저 해결 |
| 진행 상황 스트리밍 | 기다리는 동안 상태를 보여줌 | 실제 완료 시간을 줄이는 기능은 아님. 끊긴 출력을 정상 답신으로 기록하면 안 됨 |
| 후크·플러그인·MCP 자동 로딩 비용 확인 | 시작 단계의 불필요한 작업을 찾을 가능성 | 적용 중인 지침·인증·도구 제한을 보존하면서 별도로 계측 |

현재 측정만으로 네트워크·인증·모델 추론 중 어느 것이 주 병목인지 확정하지 않는다. 모델 변경·상주 브리지·캐시·자동 반복은 이번 작업에서 구현하지 않는다.

CLI의 JSON/stream-json 출력과 세션 제어는 [공식 비대화 실행 문서](https://code.claude.com/docs/en/headless), 추론 수준 등의 옵션은 [CLI 문서](https://code.claude.com/docs/en/cli-reference)를 참고한다. 시작 지연을 줄이는 `--bare`는 구독 OAuth 인증을 사용하지 않으므로 현재 로그인 경로에 바로 적용하지 않는다. 별도 API 인증으로 바꾸는 것을 속도 개선의 기본값으로 삼지 않는다.
