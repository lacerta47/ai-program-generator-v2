# LUN 비생성 영역 프로젝트 종합 점검

- 점검일: 2026-09-11
- 범위: 제품·사업성, UX·접근성, 인증·보안, 개인정보·콘텐츠 안전, Firestore·서버, 운영·배포, 테스트·유지보수
- 제외: 생성 결과의 내용·디자인 품질, 프롬프트 개선, 생성 API 호출 및 생성 샘플 테스트
- 방식: 저장소 정적 점검, 설정·문서·규칙·API 흐름 대조, 로컬 의존성 감사
- 후속 상태: P0 의존성 보안 패치 완료 (`next@15.5.25`, critical/high 0)

## 1. 결론

LUN은 단순 시제품을 넘어 **학생용 생성 흐름, 교사 관리, 학급 게시판, 공유, 신고, 사용량 통제까지 하나의 교육 서비스로 연결된 상태**다. 특히 생성 코드를 별도 오리진의 샌드박스 iframe에서 실행하고, Firestore 규칙에서 소유권·학급 범위·필드 허용목록을 강제한 점은 유사 초기 서비스보다 탄탄하다.

다만 현재 병목은 기능 수가 아니라 **운영 안전망**이다. 다음 네 가지를 해결하지 않은 채 사용 학교와 학생 수를 늘리면 장애·보안·개인정보 대응 비용이 빠르게 커질 가능성이 높다.

1. 점검 당시 설치된 Next.js의 critical 보안 취약점은 15.5.25 패치와 안전한 전이 의존성 고정으로 조치했다.
2. 교사·학생 계정 생성이 Auth와 Firestore에 걸친 비원자 작업인데 실패 보상 처리가 없다.
3. 아동 대상 공개 게시물의 금칙어 검사가 클라이언트에만 있어 직접 SDK 쓰기로 우회할 수 있다.
4. 핵심 API·Firestore 규칙·브라우저 흐름을 지속 검증하는 CI와 통합 테스트가 없다.

**종합 판정: 제한된 교사 파일럿은 가능하나, 공개 확장·유료 판매 확대 전에는 아래 P0/P1 조치가 필요하다.**

## 3. 확인된 강점

### 3.1 제품과 사업 경쟁력

- `PRODUCT.md`의 성공 정의인 “아이가 어른 도움 없이 첫 프로그램을 만들고 게시”하는 흐름이 `/easy`, `/create`, `/board`, `/mypage`로 실제 연결돼 있다.
- 일반 생성기뿐 아니라 설문형 쉬운 만들기, 고치기, 이어 만들기, ZIP 저장, 게시판 전시가 있어 **일회성 AI 데모보다 학습 활동의 순환 구조**에 가깝다.
- 교사 계정, 학생 일괄 발급, 개인·학급 한도, 학급 게시판, 관람 PIN, 신고함, 학습 개념 인사이트가 있어 B2C 도구보다 **학교·방과후·교육기관 파일럿에 적합한 운영 기능**을 갖췄다.
- 교육 지도안과 멘토용 자료가 이미 있어 소프트웨어 단품이 아니라 수업 패키지로 제안할 기반이 있다.

### 3.2 보안과 데이터 설계

- 생성 코드는 메인 앱과 다른 오리진에서 `sandbox allow-scripts`로 실행되고 `frame-ancestors`가 제한된다. 직접 탐색도 차단한다 (`lib/server/previewHeaders.ts`, `app/api/preview/[id]/route.ts`).
- Firestore는 게시물 필드 허용목록, 코드·계획서 크기, 소유권, 역할, 학급 카테고리와 `boardTeacherUid`의 일치를 규칙에서 검증한다 (`firestore.rules:58-83`, `firestore.rules:151-185`).
- 학급 글은 담당 교사·해당 반 학생·관리자에게만 읽기를 허용하고, 공개 미리보기 GET 경로에서도 학급 글을 거부한다.
- 좋아요와 조회는 서버에서 중복 방지하고, 게시물 삭제 시 하위 카운터와 신고를 정리한다.
- 관리자·교사 API는 `verifyIdToken(..., true)`로 폐기된 토큰까지 검사하고 서버 역할 게이트를 통과해야 한다.
- 사진은 학생·교사 화면에만 노출되고 별도 국외 이전 동의를 받은 뒤 첨부할 수 있으며, 공개 게시판에는 저장할 수 없도록 규칙이 제한한다.

### 3.3 비용과 초기 운영 적합성

- Firestore 커서 페이지네이션과 필요한 복합 인덱스가 적용돼 있다.
- 생성·미리보기·카운터·공유 PIN에 서버 레이트리밋이 있고, 일일 사용량·토큰 비용·게이트 탈락 통계도 집계한다.
- Vercel + Firebase의 관리형 구조는 현재 단계에서 인프라 운영 부담이 낮다.

## 4. 우선순위별 문제와 조치

### P0 — 즉시 조치 (완료)

#### P0-1. Next.js critical 취약점

**근거**

- 점검 당시 설치 버전은 `next@15.5.20`이었다.
- 최초 `npm audit --omit=dev` 결과는 critical 1, high 2, moderate 9로 총 12건이었다.
- Next.js 직접 의존성에 서버 액션·이미지 처리 관련 critical/high 권고가 연결돼 있고, 감사 결과상 안전 범위는 적어도 15.5.24 이상이다.

**영향**

- 현재 배포 환경에서 모든 취약 경로가 실제 사용되는지는 별도 확인이 필요하지만, 인터넷에 공개된 Next.js 서버의 critical 직접 의존성은 노출 여부를 추정해 방치할 사안이 아니다.

**조치**

1. Next.js를 15.5.25로 올렸다.
2. PostCSS 8.5.28, Sharp 0.35.4, protobufjs 7.6.6 이상을 `overrides`로 고정해 기존 critical/high 전이 취약점을 제거했다.
3. `npm test` 74건, `tsc --noEmit`, 40개 경로 프로덕션 빌드가 통과했다.
4. 재감사 결과 critical/high는 0이고, `firebase-admin@13.10.0`의 전이 moderate 8건만 남았다. 이 항목은 Node 22 이상을 전제로 14.x 업그레이드를 별도 작업에서 검증한다.

### P1 — 공개 확장 전 필수

#### P1-1. 계정 생성 부분 실패와 고아 계정

**근거**

- 교사 생성은 Auth 사용자 생성 → custom claim → `teachers` 문서 → `schools` 문서를 순서대로 쓴다 (`app/api/admin/teachers/route.ts:73-79`).
- 학생 생성도 각 학생마다 Auth 사용자 → claim → `students` 문서를 순서대로 쓴다 (`app/api/teacher/students/route.ts:91-110`).
- 중간 단계 실패 시 앞 단계의 Auth 사용자나 claim을 되돌리는 보상 처리가 없다.

**문제 시나리오**

- Auth 생성 뒤 Firestore 쓰기가 실패하면 로그인 계정은 존재하지만 교사/학생 레코드가 없다.
- 재시도하면 이메일 중복으로 넘어가 자동 복구되지 않는다.
- 교사는 일부 학생만 생성된 사실을 확인할 수 있지만, 고아 Auth 계정은 일반 화면에서 정리하기 어렵다.

**권장 조치**

- 최소 수정: 실패 시 방금 만든 Auth 사용자를 삭제하는 보상 처리와 구조화된 오류 로그를 추가한다.
- 더 안전한 방향: 작업 상태 문서와 idempotency key를 두어 재시도가 기존 계정을 복구하도록 한다.
- 학생 일괄 생성은 성공·실패뿐 아니라 실패 단계와 재시도 가능 여부를 반환한다.

#### P1-2. 공개 게시물 검열의 직접 SDK 우회

**근거**

- 제목·작성자명·계획서 금칙어 검사는 `lib/firebase/posts.ts:78-119`의 클라이언트 함수에서 수행된다.
- 실제 게시물 쓰기는 클라이언트가 Firestore에 직접 하며, 규칙은 문자열 형식과 소유권은 검사하지만 금칙어 목록을 검사할 수 없다.
- 코드 주석도 SDK 우회는 신고로 대응한다고 명시한다 (`lib/firebase/posts.ts:95`).

**영향**

- 아동이 보는 공개 게시판에 부적절한 제목·작성자명·계획서가 사후 신고 전까지 노출될 수 있다.
- 악의적 사용자는 정상 UI를 거치지 않아도 된다.

**권장 조치**

- 공개 게시물 생성·수정을 인증 서버 API로 옮기고 서버에서 동일 검열을 강제한다.
- 학급 글도 교사 정책에 따라 같은 서버 검열을 적용하되, 기존 Firestore 규칙은 방어층으로 유지한다.
- 관리자 긴급 숨김 상태와 신고 처리 목표시간을 정한다. 삭제만 제공하기보다 `hidden/moderationStatus`가 운영상 안전하다.

#### P1-3. 보존기간 고지는 있으나 자동 집행이 없음

**근거**

- 개인정보처리방침은 교사 삭제로 정지된 학생 계정을 1년 이내 파기한다고 명시한다 (`app/privacy/page.tsx:193-195`).
- 실제 교사 삭제는 산하 학생 Auth 계정을 비활성화하지만 정지 시각을 기록하지 않는다 (`lib/server/deleteAccount.ts:40-45`).
- 등록된 Vercel cron은 미리보기·공유 시도 정리 하나뿐이며, 1년 경과 학생을 파기하는 작업은 없다 (`vercel.json`).

**영향**

- 실제 보존 상태와 공개 고지가 장기간 어긋날 수 있고, 학교의 삭제 요청 대응도 수작업에 의존한다.

**권장 조치**

- 교사 삭제 시 학생 문서에 `disabledAt`, `disabledReason`을 기록한다.
- 정기 파기 작업을 추가하되 바로 삭제하지 말고 대상 산출 → 관리자 검토 → 실행 → 감사 로그 순서로 운영한다.
- 학교 단위 내보내기·삭제 요청 절차와 복구 불가 시점을 문서화한다.

#### P1-4. 핵심 경계에 대한 자동 회귀 테스트와 CI 부재

**근거**

- 현재 11개 테스트 파일은 프롬프트·검증·설문·금칙어·학생 쿼터 등 순수 로직 중심이다.
- API 인증/인가, 계정 생성 실패 보상, Firestore 규칙, 삭제 캐스케이드, 실제 브라우저 사용자 흐름을 정규 테스트로 실행하지 않는다.
- 저장소에 `.github/workflows`가 없고 `npm run lint`는 설정 마법사를 띄우며 종료되어 비대화형 검사로 작동하지 않는다.

**영향**

- 보안 규칙이나 API 게이트 회귀가 타입 검사와 빌드만 통과할 수 있다.
- Vercel 빌드 성공이 권한·데이터 정합성·접근성 성공을 보장하지 않는다.

**권장 조치**

1. ESLint를 명시 설정하고 `npm run lint`를 비대화형으로 고친다.
2. GitHub Actions에서 install → lint → unit test → typecheck → build를 실행한다.
3. Firebase Emulator 기반 규칙 테스트를 추가한다: 공개/학급 읽기, 역할별 쓰기, 필드 위조, 닉네임, 신고.
4. Playwright 핵심 E2E를 소수만 둔다: 가입 제한, 로그인, 만들기 진입, 게시·삭제, 교사 학생 관리. 생성 API는 mock으로 대체해 비용과 품질 테스트를 분리한다.

#### P1-5. 오류 감지·복구 체계가 코드에 보이지 않음

**근거**

- 서버 오류는 주로 `console.error`로 남고, 오류 추적·알림·상관관계 ID 도구는 확인되지 않았다.
- 배포 문서는 Vercel 코드 롤백은 설명하지만 Firestore 백업·복구 목표와 복원 훈련은 없다.

**영향**

- 계정 일부 생성, 파기 실패, 신고함 장애 같은 문제를 사용자가 알려주기 전까지 놓칠 수 있다.
- 코드 롤백은 데이터 오삭제·규칙 오류·운영자 실수를 복구하지 못한다.

**권장 조치**

- 먼저 오류 추적 서비스 또는 구조화 로그 + 알림을 연결하고 요청 ID, 사용자 역할, 작업 종류, 실패 단계를 남긴다. 원문 계획서·사진·토큰은 로그에 남기지 않는다.
- Firestore 정기 백업, 보관기간, RPO/RTO, 실제 복원 리허설 절차를 정한다.
- 생성 성공률과 별도로 로그인 실패율, 게시 실패율, 계정 작업 실패율, 신고 미처리 시간을 대시보드화한다.

### P2 — 파일럿 운영 중 개선

#### P2-1. 닉네임 유일성 규칙 우회

- `nicknames/{key}` 점유 문서는 별도로 존재하지만 `users.nickname` 쓰기에서 점유자를 교차 검증하지 않는다 (`firestore.rules:202-240`).
- 직접 SDK 쓰기로 다른 일반 사용자의 표시 닉네임을 중복 사용해 사칭할 수 있다.
- 닉네임 변경을 서버 트랜잭션으로 일원화하거나, 정규화 키를 서버에서 계산해 점유 문서와 원자 갱신해야 한다.

#### P2-2. 대량 계정 삭제의 시간제한과 부분 완료

- 학생 일괄 삭제는 최대 100명을 60초 함수에서 순차 처리한다 (`app/api/teacher/students/bulk/route.ts:73-106`).
- 학생마다 게시물·하위 컬렉션·신고·사용량 조회와 삭제가 발생해 데이터가 많으면 시간 초과와 부분 완료가 가능하다.
- 한 요청 상한을 낮추고 작은 배치+재개 토큰을 제공하거나, 작업 큐로 옮겨 완료 상태를 보여주는 편이 안전하다.

#### P2-3. 토큰 폐기 확인 정책 불일치

- 관리자·교사·생성 API는 `verifyIdToken(token, true)`를 사용하지만 미리보기, 게시물 삭제·카운터, 본인 사용량·탈퇴, 학생 보드 API는 기본 검증만 사용한다.
- 정지된 학생의 기존 ID 토큰이 만료되기 전까지 일부 서버 API를 계속 호출할 수 있다.
- 권한·개인정보·쓰기 작업은 공통 인증 헬퍼로 통일하고 폐기 확인 여부를 명시적으로 분류한다.

#### P2-4. 관리자 조회 비용과 성장 한계

- 관리자 사용자 목록 한 페이지가 사용자별 게시물 `count()`를 50회 실행하고, 7일 사용량 문서를 최대 350개 읽는다 (`app/api/admin/users/route.ts:15-38`).
- 일일 통계는 매번 모든 Firebase Auth 사용자를 순회한다 (`app/api/cron/daily-stats/route.ts:14-23`).
- 소규모에는 허용되지만 사용자 수 증가 시 지연과 비용이 선형 증가한다. 사용자 통계 요약 문서를 이벤트 시 갱신하거나 일별 집계로 전환해야 한다.

#### P2-5. 레이트리밋 청소 쿼리의 요청 경로 결합

- 고정 윈도우 요청이 허용될 때마다 만료 문서 청소 쿼리를 비동기로 실행한다 (`lib/server/rateLimit.ts:7-35`, `lib/server/sharePin.ts:42-57`).
- 공격 방어 자체는 좋지만 정상 요청마다 추가 쿼리 비용이 붙는다.
- Firestore TTL 또는 정기 cron으로 책임을 옮기고, 요청 경로의 청소는 낮은 확률로 샘플링하는 편이 낫다.

#### P2-6. 개인정보 최소화와 공개 열람 범위

- `users`, `nicknames`, `schools`, 게시물 좋아요 하위 문서는 공개 읽기다 (`firestore.rules:187-240`, `firestore.rules:277-280`).
- 사용자 문서는 닉네임 중심이라 민감도는 낮고 학교 목록 공개는 학생 로그인 UX상 의도된 선택이지만, 학교·교사 UID 열거와 UID별 좋아요 관계는 최소화 여지가 있다.
- 공개로 필요한 필드만 별도 디렉터리 문서에 두고, 내부 UID 대신 불투명 공개 식별자를 쓰는 방안을 검토한다.

#### P2-7. 아동 UX 기준과 실제 글자 크기 불일치

- 제품 기준은 본문 17~18px, 주요 버튼 48px 이상이다 (`PRODUCT.md:30`, `DESIGN.md:46`).
- 생성 결과, 게시판, 로그인, 교사 화면에 12.5~16px 텍스트가 반복적으로 사용된다. 보조 정보에는 일부 허용할 수 있지만 오류·동의·안내까지 작은 경우가 있다.
- 우선 로그인 동의, 사진 동의, 오류, 게시·삭제, 학생용 안내를 17px 기준으로 감사하고 터치 대상 44/48px와 키보드 포커스를 자동 검사한다.

### P3 — 성장 단계 최적화

#### P3-1. 성공 지표가 방문·가입·생성·게시 건수에 치우침

- 현재 운영 통계는 방문, 가입, 생성 횟수, 게시물, 신고, 토큰 비용에 집중한다.
- 제품의 진짜 성공인 “아이가 도움 없이 완성·게시”와 교사 가치인 “한 학급이 반복 사용”을 측정하기 어렵다.

**권장 퍼널**

1. 만들기 화면 진입
2. 첫 입력 또는 설문 시작
3. 생성 시도
4. 미리보기 확인
5. 수정 요청 또는 완성 선택
6. 다운로드·게시
7. 7일/30일 내 재방문 및 재생성

개별 아동을 광고 목적으로 추적하지 말고, 최소 이벤트와 학급 단위 집계로 activation, completion, publish, D7 classroom retention을 본다.

#### P3-2. 상품화 기준 정립 필요

- 기술적으로 교사 파일럿이 가능하지만 가격·지원범위·장애 공지·데이터 삭제 요청·학기 종료 절차가 제품 화면과 운영 문서로 완결돼 있지 않다.
- 초기 상품은 “학생 수 × 월 구독”보다 **학급/회차 패키지**가 현재 총 쿼터와 교육자료 구조에 잘 맞는다.
- 유료 전환 판단 전 최소 3~5개 학급에서 첫 수업 완주율, 교사 준비시간, 학생 1인당 생성비용, 신고·지원 건수, 다음 수업 재사용 의향을 측정한다.

## 5. 권장 실행 순서

### 1단계: 1~3일 — 노출 위험 차단

1. Next.js 보안 패치와 잠금파일 갱신
2. 비대화형 lint 구성
3. 핵심 검사 CI 추가
4. 패치 후 스모크 테스트와 배포

**완료 기준:** critical 직접 의존성 0, PR마다 lint/test/typecheck/build 자동 통과.

### 2단계: 1주 — 계정·게시 안전성

1. 교사/학생 생성 실패 보상과 재시도 가능 응답
2. 계정 수명주기 상태·실패 로그
3. 공개 게시 생성/수정 서버화와 서버 금칙어 검사
4. 닉네임 점유 원자화

**완료 기준:** 각 단계 강제 실패 테스트에서 고아 계정·중복 닉네임·검열 우회가 남지 않음.

### 3단계: 1~2주 — 데이터·운영 안전망

1. Firestore Emulator 규칙 테스트
2. 오류 추적·알림 및 개인정보 비기록 정책
3. 정기 백업과 복원 리허설
4. 정지 학생 보존기간 자동 집행

**완료 기준:** 장애를 운영자가 먼저 탐지하고, 테스트 프로젝트에서 백업 복원과 기간 만료 파기를 증명.

### 4단계: 파일럿 병행 — UX와 사업 검증

1. 학생 핵심 화면 글자·터치·키보드·스크린리더 점검
2. 최소 퍼널 계측
3. 3~5개 학급 파일럿 운영
4. 학급 단위 가격과 지원·삭제 절차 확정

**완료 기준:** 첫 작품 완성률, 게시 전환률, 수업 재사용률, 교사 준비시간, 학생당 원가를 숫자로 판단 가능.

## 6. 제안하는 첫 작업 묶음

생성 품질을 멈춘 현재 가장 적절한 첫 묶음은 아래다.

1. **보안 패치:** Next.js 패치 업데이트 — 완료
2. **검사 기반:** ESLint + GitHub Actions — 다음 권장 작업
3. **회귀 보호:** 인증 API 3~5개와 Firestore 핵심 규칙 테스트 골격

이 묶음은 제품 동작을 크게 바꾸지 않으면서 이후 모든 수정의 안전도를 높인다. 그다음 계정 생성 보상 처리와 게시물 서버 검열을 진행하는 순서가 효율적이다.

## 7. 점검 한계

- 프로덕션 Firebase 콘솔의 App Check 강제 여부, IAM, 실제 백업 설정, Vercel 로그·알림은 저장소만으로 확인할 수 없었다.
- 실제 사용자 데이터, 운영 로그, 트래픽, 비용 청구서는 조회하지 않았다.
- 브라우저 매트릭스, 화면별 접근성 자동 검사, 부하·장애 주입 테스트는 수행하지 않았다.
- 생성 API를 호출하지 않았고 생성 품질을 평가하지 않았다.
- 법적 적합성을 확정하는 법률 검토가 아니라, 공개 고지와 구현의 일치 여부를 기술적으로 점검했다.
