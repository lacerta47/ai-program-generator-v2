# BizRouter 우선 · 혼잡 시 Gemini 분산

2026-10-31. 운영 활성화 요청에 맞춘 정책이다. PR #167에 반영했으며 Production 설정 5개 등록을 완료했다. 이 기록 시점에는 CI·병합 및 새 운영 배포 확인 전이다.

## 동작

- `AI_PROVIDER=bizrouter-first`로 활성화한다. `split`은 앞선 50:50 비교 모드이며 별도로 유지한다.
- 사용자 요청은 먼저 BizRouter 실행 슬롯을 확보한다. 기본 4개 슬롯이 모두 사용 중인 동안 들어온 다음 요청부터 Gemini 직접 호출 슬롯을 확보한다. 임계값은 '분당 요청 수'가 아닌 '현재 진행 중인 작업 수'다.
- BizRouter에 여유가 생기면 새 요청은 다시 BizRouter부터 시도한다. 고정된 사용자나 학급을 Gemini에 영구 배정하지 않는다.
- Gemini도 기본 4개가 모두 사용 중이면 503과 Retry-After를 반환하며 생성 한도는 예약하지 않는다.
- 두 경로는 일반 Gemini 3.8 Flash, 미로·꾸미기·수족관 Gemini 4 Argon 배정을 유지한다. 무료 자동 예시는 기존 Gemini 경로다.
- DB 오류·인증 오류·실행 중 공급사 오류는 '슬롯 부족'과 구별한다. 실행 중인 요청을 다른 경로에서 자동 재생성하지 않는다.

## 운영 설정

Vercel Production에 두 키는 이미 등록돼 있음을 값 열람 없이 확인했다. 추가할 값은 다음 비밀이 아닌 설정이다.

```text
AI_PROVIDER=bizrouter-first
BIZROUTER_MODEL=google/gemini-3.8-flash
BIZROUTER_HIGH_MODEL=google/gemini-4-argon
GEN_BIZROUTER_CONCURRENCY=4
GEN_GEMINI_CONCURRENCY=4
```

1. 변경 소스와 전체 검사를 확인한 뒤 커밋·푸시 승인을 받는다. 생성 시험 출력과 `.env.local`은 업로드하지 않는다.
2. PR CI를 통과하고 병합한다. 새 정책의 환경변수가 적용되는 새 Production 배포를 확인한다. 환경변수만 저장한 상태를 운영 활성화 완료로 보고하지 않는다.
3. 서버 전용 슬롯 컬렉션의 거부 규칙 배포도 확인한다. 문서 ID 직접 접근이므로 새 인덱스는 필요하지 않다. 기존 규칙의 기본 거부도 유지한다.
4. 코드 버전·배포 상태·설정 적용 여부와 공개 경로 및 비로그인 생성 차단을 점검한다. 운영에서 실제 생성·부하를 넣는 별도 시험은 승인받아 진행한다.
5. 설정을 바꾸거나 상한을 낮출 때 진행 중인 작업을 먼저 소진한다. 구버전과 새 버전이 혼재하는 동안 새 상한이 즉시 보장되지는 않는다.

## 검증 범위

2026-10-31 검사 결과: 단위 184건 통과(기존 opt-in 2건 건너뜀), API 46건 통과, Firestore 에뮬레이터 42건 통과. 타입·린트·프로덕션 빌드 통과. 빌드에는 공개 Firebase 설정의 CI용 가상 값을 사용했다. 로컬 설정은 bizrouter-first로 적용했으며 운영은 새 코드 배포가 필요하다.

- 단위 모의 검사: 평시 BizRouter 선택, 슬롯 부족 시에만 Gemini 선택, 품질 전달, 두 경로 포화 거부, DB 오류 시 전환 금지, 실행 중 오류 시 이중 호출 금지를 확인한다.
- 에뮬레이터 실제 트랜잭션 검사: 2개씩의 슬롯을 사용해 처음 두 작업은 BizRouter, 다음 두 작업은 Gemini, 다섯 번째는 포화 거부되는지 확인한다. BizRouter 슬롯 해제 후 다음 작업이 다시 BizRouter를 쓰는지도 확인한다. 공급사 호출은 모의 처리한다.
- 앞선 실제 10회 시험에서 동일 모델의 양쪽 호출은 성공했다. 새 우선 배정 정책의 실제 대규모 수업 용량을 검증한 결과는 아니다.

## 되돌리기

새 배포에서 설정·라우팅 이상이 있으면 이전 정상 배포로 되돌린다. 분산을 끄려면 `AI_PROVIDER=gemini` 또는 `bizrouter`로 바꿔 새로 배포한다. 단독 모드는 기존 방식으로 동작하며 이 공유 슬롯 제어를 사용하지 않는다.
