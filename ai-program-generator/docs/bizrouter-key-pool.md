# BizRouter 키 두 개 연결

등록 이름은 기본 `BIZROUTER_API_KEY`, 추가 `BIZROUTER_API_KEY_2`다. 추가 키는 선택 사항이며 없으면 기존 기본 키만 사용한다. 실제 값은 로컬 `.env.local` 또는 Vercel의 서버 전용 Secret에 등록한다.

## 요청 배정

운영의 `bizrouter-first` 모드에서는 서버 공통 슬롯을 먼저 확보한다. 슬롯 번호 0·2·4·6·8은 기본 키, 1·3·5·7·9는 추가 키를 사용하므로 운영 10개 슬롯을 모두 사용하는 상황에서는 키마다 5건씩 처리한다. 한 건만 실행되는 상황에서는 확보된 슬롯에 따라 어느 키든 선택될 수 있다.

운영은 `GEN_BIZROUTER_CONCURRENCY=10`, `GEN_GEMINI_CONCURRENCY=4`로 설정한다. BizRouter 10개가 모두 차면 Gemini 직접 호출 경로로 넘기며, 두 경로의 총 14개가 모두 차면 503과 Retry-After로 재시도를 안내하고 생성 한도는 예약하지 않는다. 환경변수가 없는 환경의 라이브러리 기본 상한은 기존 4개를 유지한다. 50:50 비교 모드에도 같은 키 배정 방식을 적용한다. 슬롯을 거치지 않는 내부 호출은 요청 ID를 해시해 키를 배정한다.

한 요청은 처음 정한 키로 끝까지 호출한다. 인증·권한 오류나 응답 중 오류를 다른 키로 자동 재호출하지 않는다. 기본·복잡 모델 배정은 Gemini 3.8 Flash / 4 Argon을 유지한다. 두 키 모두 해당 모델 접근 권한이 있어야 한다.

## 보관 및 운영 반영

- 로컬 추가 등록: `powershell -ExecutionPolicy Bypass -File scripts/set-bizrouter-key.ps1 -Provider bizrouter2`.
- 운영 추가 등록: Vercel Production에 Secret 이름 `BIZROUTER_API_KEY_2`를 추가하고 새 코드로 배포한다. 로컬에서 운영으로 키 값을 자동 복사하지 않는다.
- 키 원문·일부 문자열은 로그·프롬프트·Firestore에 기록하지 않는다. 슬롯 문서의 필드는 그대로 owner·expiresAt이며 새 인덱스나 규칙 변경이 필요하지 않다.
- 키 하나를 더 쓰는 것이 계정의 실제 처리 용량 증설을 보장하지 않는다. 이번에는 사용자 승인으로 서버 상한을 10개로 조정했으며 실제 공급사 부하 시험은 별도 승인이 필요하다.

## 2026-10-31 검증

추가 키의 모델 목록 API 인증(HTTP 200)과 두 Gemini 모델의 허용 상태를 확인했다. 생성 API는 호출하지 않았다. 두 키의 Authorization 헤더 사용과 키별 오류의 비재시도는 모의 HTTP 응답으로 검증했다. 에뮬레이터의 실제 슬롯 4개 및 10개에서 키별 균등 배정과 초과 요청의 Gemini 분산을 확인했다. 운영 10+4개가 모두 찬 뒤 다음 요청의 포화 거부도 통과했다. 10개 상한에서는 동시에 16개 슬롯을 요청해 10개만 확보하고 짝수·홀수 위치가 각각 5개임을 단위 검사했다. 단위 189건·API 46건·Firestore 에뮬레이터 44건, 타입·린트·프로덕션 빌드 통과. 빌드에는 공개 Firebase 설정의 CI용 가상 값을 사용했다.
