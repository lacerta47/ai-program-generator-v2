# Gemini 직접 호출 / BizRouter 호출 분리 계획

작성: 2026-10-31. 설계 검토 자료이며 호출 분산은 아직 구현하지 않았다. 실제 생성·부하 시험과 커밋·푸시는 사용자 승인 후 진행한다.

진행 상황: 같은 날 [1차 구현 및 검증 기록](provider-split-progress-2026-10-31.md)에 코드·검사 결과를 추가했다. 콘솔에서 BYOK 미연동과 Tier 1의 분당 60회·동시 60회도 확인했다. 아래 미확인 항목은 계획 작성 당시 상태이며, 최신 확인 결과는 진행 기록을 기준으로 한다. 실제 활성화·운영 배포 및 생성 시험은 아직 하지 않았다.

## 현재 확인 결과

- `lib/ai/provider.ts`: AI_PROVIDER=bizrouter이면 사용자 생성은 BizRouter, tier=free 자동 예시는 Gemini 직접 호출이다. 학생 요청을 두 경로에 분산하지 않는다.
- 같은 모델 유지: 일반은 Gemini 3.8 Flash, 미로·꾸미기·수족관은 Gemini 4 Argon. BizRouter에는 google/ 접두어를 붙인 모델 ID를 사용한다.
- `lib/ai/bizrouter.ts`: 서버에서 Authorization: Bearer 인증으로 https://api.bizrouter.ai/v1/chat/completions에 요청한다. model을 구체적으로 지정하고 SSE 스트림 및 JSON Schema를 요청한다. 현재 bizrouter/route 스마트 라우팅은 사용하지 않는다.
- 실제 키로 GET /v1/models를 조회한 결과 HTTP 200이며 위 두 모델을 확인했다. 생성 요청은 보내지 않았다. RateLimit / Retry-After 헤더는 이 응답에 없었다. 모델 목록 포함은 실시간 생성 성공을 보장하지 않는다.
- 현재 작업 폴더에는 BizRouter 키만 있고, 원래 프로젝트 폴더에는 Gemini 키만 있다. 분산 구현 시 두 서버 자격 증명을 같은 실행 환경에 사용자가 등록해야 한다. 키 원문을 다른 폴더로 복사하지 않았다.

## BizRouter 호출 구조

서비스 키 인증 → 조직·키의 접근 정책 및 한도 확인 → 요청한 모델에 대한 제공사 선택 → 외부 모델 실행 → 스트림·사용량 응답으로 이해할 수 있다. 이는 공식 문서의 기능을 정리한 흐름이며 내부 구현 순서를 보장하는 설명은 아니다.

- 모델 허용 범위와 IP/CIDR 제한, 조직 월 한도, 키별 크레딧 한도, 분당 호출 제한과 키별 rate override가 적용될 수 있다. [인증 문서](https://bizrouter.ai/docs/authentication)
- 같은 모델을 여러 제공사가 제공하면 BizRouter가 제공사를 선택한다. 허용된 키에서는 x-bizrouter-provider로 제공사를 지정할 수 있다. 구체 모델 지정과 bizrouter/route의 모델 자동 선택은 다른 기능이다. 현재 조직의 폴백 정책이 실제 요청에 미치는 영향은 별도 확인 대상이다. [전환 문서](https://bizrouter.ai/docs/migration)
- BYOK는 우리 소유의 제공사 키를 BizRouter에 등록해 사용하는 방식이다. 이 경로가 직접 호출과 같은 Google 프로젝트를 사용한다면 그 프로젝트의 한도를 공유할 수 있으므로 독립 용량으로 계산하지 않는다. 현재 키의 BYOK 사용 여부는 확인되지 않았다. [BYOK 설명](https://bizrouter.ai/docs/enterprise), [Google 프로젝트별 한도](https://ai.google.dev/gemini-api/docs/rate-limits)
- 조직·키의 결제 한도와 진행 중 요청의 크레딧 예약도 호출에 영향을 줄 수 있다. HTTP 403은 영구 잔액 부족과 일시 예약 문제 등을 오류 코드로 구분해야 한다. 현재 어댑터는 HTTP 상태만 남기므로, 공식 오류 코드 중 허용된 값만 보존하는 보강이 필요하다. 응답 본문 전체나 키를 로그에 남기지 않는다. [인증 문서](https://bizrouter.ai/docs/authentication)
- 별도 Usage API 키로 비용·요청 로그 메타데이터를 조회할 수 있고 is_byok 항목도 제공한다. 기존 모델 호출 키와는 별도 인증이다. 현재 Usage API 키는 등록·호출하지 않았다. [사용량 조회 문서](https://bizrouter.ai/docs/usage-api)

## 먼저 확인할 계정 정보

대시보드 또는 제공사 답변으로 확인할 항목:

1. 현재 키는 BizRouter 종량제 자격 증명으로 호출하는가, BYOK인가? Gemini 모델별 실제 공급 경로와 우리 Google 프로젝트의 분당 한도에서 독립적인가?
2. 조직·키·Gemini 각 모델의 RPM/TPM, 동시 스트림 상한, 키별 rate override와 일일/월 한도는 얼마인가? 키를 추가해도 공유되는 상위 한도는 무엇인가?
3. 429/503 재시도 권장 방식, Retry-After 제공 여부, 요청 취소 후 공급사 비용과 크레딧 예약 해제 시점은 무엇인가?
4. 고정 모델 요청에도 조직 정책으로 모델 또는 제공사가 바뀔 수 있는가? 실제 선택 모델·제공사를 어떤 로그로 확인하는가?

광고 문구나 키 개수만으로 무제한 동시 호출 또는 2배 용량을 가정하지 않는다. 위 질문을 외부에 발송하지 않았다.

## 구현 단계

### 1. 같은 모델로 호출 경로만 나누기

- 제공자 선택은 기존 원칙대로 lib/ai/provider.ts 안에 둔다. 앱은 AIProvider 계약을 계속 사용한다.
- Gemini 전용 / BizRouter 전용 / 분산의 세 운영 모드와 즉시 되돌릴 환경설정을 준비한다. 무료 자동 예시는 별도 경로로 유지한다.
- 시작 비율은 Gemini 직접 50%, BizRouter 50%를 시험 가설로 사용한다. 요청 ID에 기반한 안정된 배정으로 같은 요청의 재처리 때 공급 경로가 임의로 바뀌지 않게 한다. 학급별 편중이 없는지도 기록한다.
- 기본·복잡 모델 배정은 그대로 유지한다. 이번 단계에서 Opus 등 다른 모델로 자동 변경하지 않는다.
- 분산 설정에는 두 키가 모두 필요하다. 누락 시 호출 전 설정 오류를 표시하고 임의의 경로로 전량 몰아 보내지 않는다.

### 2. 서버 전체의 동시 실행 수 제어

- 초기 시험값은 경로별 최대 4개, 합계 8개 동시 실행이다. 확인된 한도가 더 낮으면 낮춘다. 이 수치는 처리 능력의 보증이 아니며 기존 모델 응답시간과 재측정으로 조정한다.
- Vercel 인스턴스의 메모리 카운터만으로 제한하면 서버 여러 대에서 한도를 초과한다. 공유 저장소의 경로별 소수 슬롯 문서를 트랜잭션으로 확보하는 임대 방식부터 검토한다. 단일 전역 카운터 문서에 모든 요청을 집중시키지 않는다.
- 슬롯은 소유 요청 ID와 만료 시간을 갖고, 긴 생성 중에는 갱신한다. 정상 완료·실패·취소 시 해제하고 프로세스 장애 시 임대 만료로 회복한다. 만료 정리는 Firestore TTL 삭제 시점에 의존하지 않는다.
- 인증·입력 검증·사용자 시작 빈도 제한 이후 슬롯을 확보하고, 학생 한도 예약은 생성 직전 한 번만 수행한다. 취소·실패 환불과 사용량 기록도 기존 의미를 유지한다. 활성 슬롯 없이 공급사 호출이 시작되지 않게 한다.
- 대기 슬롯 부족은 명확한 재시도 안내로 처리하고, HTTP 요청을 오래 붙잡아 두는 인메모리 대기열은 만들지 않는다. 여러 학생에게 동일한 고정 재시도 시간을 주지 않고 지연에 작은 무작위 차이를 둔다.

### 3. 수업용 대기열은 필요 시 별도 단계로

- 30명 동시 시작 시험에서 기다림이 길다면 학급 간 공정 순서와 취소 가능한 영속 대기열을 추가한다. 학급별 큐를 번갈아 처리해 한 수업이 전체 슬롯을 차지하지 않게 한다.
- 영속 대기열은 작업 ID·소유권·만료·상태 전이를 검증하고, 대기 중에는 생성 한도를 차감하지 않는다. 동일 요청 ID는 하나의 작업만 만든다.
- 별도 작업자나 관리형 작업 실행기를 사용해 서버리스 응답 종료 후 계속 실행된다고 가정하지 않는다. Vercel 실행시간·스트림 재연결·결과 전달·추가 비용을 먼저 검토하고 실행기를 결정한다. 1차 분산 구현에 대기열 전체를 끼워 넣지 않는다.
- Firestore 문서나 질의를 추가하면 소유권·서버 전용 쓰기·필드 검증 규칙 및 필요한 인덱스를 함께 점검한다. 교사 풀 한도 문서의 트랜잭션 경합은 별도 관측한다.

### 4. 장애 전환은 분산 검증 뒤 제한적으로

- 초기에는 두 경로를 동시에 호출하는 경쟁 실행을 하지 않는다. 공급사 이중 과금이 발생할 수 있다.
- 사용자에게 일부 코드가 전달된 뒤에는 다른 경로로 이어 붙이지 않는다. 실패·환불을 한 번만 처리한다.
- 이후 명백한 호출 제한이나 공급사 일시 오류에 한해 제한된 재시도를 검토한다. 다른 경로도 자기 슬롯과 한도를 충족해야 한다. 최초 출력 전이라도 공급사 과금은 시작됐을 수 있어 무조건 무료 재시도라고 보지 않는다.
- 인증 오류·권한 오류·실제 잔액 소진·출력 문법 오류는 일시 과부하와 구별한다. HTTP 상태 외 공식 오류 코드와 Retry-After 등 필요한 메타데이터만 보존하고 재시도 가능 여부를 결정한다.

## 관측 및 검증

- 비밀 키·프롬프트·생성 코드 대신 요청 ID, 가명 학급 ID, 선택/실제 모델, 경로, 시도 번호, 대기시간, 첫 응답시간, 총 시간, 토큰, 비용, 429/503/timeout, 취소 및 환불 결과를 기록한다. 같은 요청의 복수 시도 비용은 모두 합산한다.
- 모의 테스트: 경로 비율 및 재현성, 모델 유지, 키 누락, 동시 슬롯 상한, 임대 만료·갱신·해제, 취소, 중복 요청, 한도 1회 차감/환불, 첫 출력 후 전환 금지, 경로별 장애를 확인한다.
- 승인받은 소량 실제 생성으로 BizRouter Gemini의 JSON Schema·사진·취소·사용량 호환성을 먼저 검증한다. 기존 300건 모델 시험은 Gemini 두 모델의 동시 학급 시험이 아니므로 이를 대체하지 않는다.
- 이후 인증된 모의 학생 30명 → 60명 → 필요 시 125~150명으로 단계 확대한다. 같은 모델/입력 분포로 Gemini 단독, BizRouter 단독, 50:50 분산을 비교한다. 정확한 요청 수와 예상 비용을 산출한 뒤 승인을 받는다.
- 제안 합격 기준: 성공률 98% 이상, 잘못된 추가 차감·중복 완료·한도 초과 실행 0건, 심각한 경합 0건. 단계별 대기/총 응답 p50·p95를 제시하고 다음 단계 확대 여부를 판단한다. 목표 시간은 실제 Flash/Argon 지연과 수업 허용 대기시간을 확인한 뒤 확정한다.
- 계정 한도가 독립적이지 않거나 분산이 단독 대비 개선되지 않으면 분산 비율을 늘리지 않고, 대기열·한도 증설·별도 유료 프로젝트 방안을 비교한다.

## 현재 결정

공식 인증·모델 허용 구조와 현재 키의 목록 접근은 확인했다. 정확한 계정 한도와 BYOK 여부는 미확인이다. 먼저 그 값을 확인하고, 같은 모델의 두 경로 + 공유 동시 실행 제한을 작게 구현하는 것이 권장 순서다. 운영 호출 방식과 자격 증명은 이번 문서 작성으로 변경하지 않았다.
