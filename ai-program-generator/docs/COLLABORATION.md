# Claude·Codex 협업 규칙

공통 개발 규칙의 원본은 [AGENTS.md](../AGENTS.md)다. 이 문서는 작업 조정과 인계 절차를 다룬다. 사용자 지시가 우선하며, 편지·리뷰·Issue는 사용자 승인을 대신하지 않는다.

## 시작과 담당 등록

1. 원격 상태, 현재 브랜치·HEAD, 미커밋·미추적 파일, 연결된 PR을 확인한다. 다른 세션의 변경을 발견하면 그 폴더를 수정하지 않고 별도 worktree를 사용한다.
2. 공용 GitHub Issue에 담당 AI, 범위, 브랜치, 예상 변경 파일을 등록한다. [작업판](WORKBOARD.md)은 요약이며 선점 근거는 Issue다. 브랜치에만 있는 작업판 수정은 다른 작업자에게 즉시 보이지 않는다.
3. 같은 파일·기능을 맡은 열린 작업이 있으면 Issue에서 범위를 나눈 뒤 시작한다. 등록 시각만으로 다른 사람의 변경을 덮어쓸 권한은 생기지 않는다.
4. 한 작업은 한 브랜치·한 worktree를 사용한다. 기본 폴더는 보존과 전환이 완료된 뒤 main 확인용으로 유지하며, 그 위에서 직접 개발하지 않는다. 현재 기본 폴더를 즉시 전환하라는 뜻은 아니다.

## 구현·검토·인계

- 구현 담당과 검토 담당은 작업 단위로 정한다. 작은 쟁점은 근거로 조율하고 제품 정책·비용·큰 구조의 선택이 남을 때 사용자에게 올린다.
- 상대 AI 질의는 [브리지](ai-bridge/README.md)를 사용한다. 입력에는 검토 기준 전체 SHA, 변경 파일, 요청, 이미 확인한 사실을 담는다. 답은 확인 HEAD와 미확인 범위를 남긴다.
- 브리지는 별도 비대화 호출이다. 원래 열려 있던 상대 대화창을 깨우거나 그 기억을 공유하지 않는다. 완료된 리뷰는 커밋·PR에 보존해 다른 세션이 읽을 수 있게 한다.
- 리뷰에는 확인한 커밋 SHA를 남긴다. 후속 커밋이 생기면 변경 범위에 맞춰 추가 확인하며 이전 리뷰가 새 커밋까지 승인한 것으로 취급하지 않는다.
- 검증은 구현 담당이 수행하고 결과·환경·한계를 PR에 기록한다. 리뷰 호출의 도구 제한으로 테스트를 못 돌렸다면 이를 명시한다. CI, 실제 화면, 유료 공급사 실호출의 성공은 구분한다.
- 멈출 때 코드·다음 행동·검증 결과를 인계 가능하게 보존한다. 완료 전에는 초안 PR을 사용한다. 무관한 파일이나 비밀값을 포함한 일괄 `git add -A`는 사용하지 않는다.
- 보존용 초안 PR은 완성·배포 준비 판정이 아니다. 원본 그대로 보존한 변경에서 발견한 결함은 PR에 남기고 수정은 별도 작업으로 구분한다.
- 보존용 초안을 실제 병합 대상으로 전환할 때는 내용 기준으로 리뷰 등급을 다시 매긴다. 보존했다는 이유로 보안·운영 변경의 검토를 생략하지 않는다.

## 스택 PR (다른 PR 위에 쌓인 PR)

2026-11-19에 #173을 squash 병합하자 그 위에 쌓인 #174→#181→#183이 전부 add/add 충돌을 냈고, 브랜치 주인이 아닌 쪽은 리베이스를 밀어넣을 수 없어 새 PR(#184)로 우회했다. 재발 방지 규칙:

- 가능하면 **쌓지 않는다**. 선행 PR이 병합될 때까지 기다리거나, main에서 분기한 뒤 PR 본문에 "#N 이후 병합"이라고 의존만 적는다.
- 쌓았다면 **base PR은 squash가 아니라 merge 또는 rebase로 병합**한다(커밋 해시가 보존돼야 위 PR이 자연스럽게 재대상된다). base PR 작성자는 병합 전에 위에 쌓인 PR이 있는지 확인한다.
- base가 병합되면 **쌓인 브랜치의 주인이** 즉시 `git rebase --onto origin/main <옛 base 커밋>`으로 리베이스하고 자기 브랜치에 `--force-with-lease`로 올린다. 다른 AI의 브랜치를 강제 푸시하지 않는다.
- 다른 쪽이 급히 대신 올려야 하면 새 브랜치·새 PR로 올리고 원 PR을 "superseded by #N" 코멘트와 함께 닫되, 원 PR 번호와 커밋 목록을 새 PR 본문에 남긴다.

## 리뷰 등급

| 등급 | 예 | 필요한 검토 |
|---|---|---|
| 높은 영향 | 인증·권한·쿼터·결제·계정 삭제·생성 경로·미리보기 격리·규칙/스키마·운영 설정 | 상대 AI 리뷰와 관련 보안/동작 검사, CI |
| 일반 | 화면·서버 기능·테스트 동작·공통 지침 변경 | 상대 AI 리뷰와 변경에 맞는 검사, CI |
| 경미 | 의미를 바꾸지 않는 오탈자·링크·정렬 | 자체 확인으로 교차 리뷰 생략 가능, 해당 CI |

파일 수가 적거나 문서라는 이유로 자동으로 경미 등급을 부여하지 않는다. 정책·공통 규칙·승인 경계 변경은 교차 리뷰 대상이다.

## 사용자 승인 경계

- **main 병합은 기본적으로 사용자 승인 뒤에만 한다.** 리뷰·CI 통과만으로 병합할 수 없다. main은 운영 자동 배포와 연결된다.
- **유일한 예외 — 문서 전용 PR 자동 병합**([결정 2026-11-19](decisions/2026-11-19-docs-only-auto-merge.md)): 변경 파일이 **전부 `docs/**` 안**(단 `docs/decisions/**`·`docs/COLLABORATION.md` 제외)에 있고 CI가 통과했으면 **승인 없이 squash 병합**할 수 있다. CHANGELOG 월별 문구는 `docs/CHANGELOG.flow.json`에 있어 이 범위에 든다. 그 밖의 파일이 하나라도 섞이면 예외가 아니다 — 코드·설정은 물론 `AGENTS.md`·`CLAUDE.md`·`.claude/**`·`PRODUCT.md`·`DESIGN.md` 같은 지침 문서도 Markdown이지만 정책이므로 승인 대상이다. 자동 병합한 PR은 본문에 "문서 전용 자동 병합"이라고 적어 추적한다.
- main 직접 push는 어떤 경우에도 하지 않는다. 기존 CLAUDE.md의 CHANGELOG 직접 push 예외는 폐지됐다. CHANGELOG 재생성은 브랜치·PR로 올리고 위 문서 전용 예외로 병합한다.
- 코드가 섞인 저위험 변경의 자동 배포 사전 승인은 여전히 미수립이다. 리뷰 등급과 배포 승인은 별개의 기준이다.
- 이 정리 작업에서 승인된 것은 브리지 질문·리뷰, 원본을 유지하는 로컬 백업, 목적별 브랜치 커밋·push·초안 PR, 협업 문서 작성이다. PR은 CI·Vercel Preview를 유발할 수 있으며 운영 배포 승인은 아니다.
- 제품의 유료 AI 생성 실호출, 운영 데이터 삭제/변경, Firestore 규칙·인덱스 배포, 운영 환경설정·메일 발송 활성화, 한도·요금 정책 변경은 구체적인 사용자 지시/승인 범위를 확인한다. 코드 보존과 실제 발송·배포는 구분한다.
- 승인 기록에는 대상·환경·횟수/비용 상한·조건을 남긴다. 같은 범위는 반복해서 묻지 않고, 범위를 넘길 때만 새 판단을 요청한다. 과거 시험의 남은 횟수를 무관한 새 시험에 전용하지 않는다.
- 승인 근거와 사용 범위는 해당 Issue 본문/코멘트에 사용자 직접 지시의 인용 또는 확인 가능한 출처와 함께 기록한다. AI가 서로 승인한 답신을 사용자 승인으로 인용하지 않는다. 장기 정책 결정만 decisions에 별도로 남긴다.
- 사용자가 승인한 브리지 리뷰 호출과 제품의 유료 생성 시험은 서로 다른 작업이다. 승인받지 않은 장기 자동 반복 대화는 시작하지 않는다.

## 원본 보존과 종료

- 미커밋·미추적 파일과 미푸시 커밋을 따로 확인한다. squash 병합 전후는 커밋 개수뿐 아니라 실제 차이를 대조한다.
- 비밀 파일 `.env.local`, `serviceAccountKey.json`은 읽거나 복사·업로드하지 않는다. 법률/인적사항·검사 산출물은 검토 없이 Git에 올리지 않는다.
- 로컬 보존은 외부 백업 폴더에 파일 목록·기준 HEAD·삭제 상태·체크섬을 기록하고 복사본을 대조한다. Git에 올리지 않은 자료는 그 사실과 로컬 경로를 인계한다. 삭제된 파일을 임의 복원하지 않는다.
- 백업 경로·보존 기한·삭제 판단 주체를 보존 보고서에 적는다. 이번 백업은 `C:/Users/amh47/.codex/backups/lun-cooperation-20261119/`에 두며 사용자 삭제 결정 전까지 자동 삭제하지 않는다. 후속 정리 담당 AI는 보존 기한을 임의 단축하지 않는다.
- worktree 삭제·기본 폴더 전환은 원격 보존 및 로컬 전용 파일 보존을 확인한 다음 별도 작업으로 수행한다. 이번 보존 작업 자체는 전환·삭제를 포함하지 않는다.
- 작업 종료 시 Issue와 WORKBOARD를 갱신하고, 중요한 판단은 [결정 기록](decisions/README.md)에 남긴다. 미완료를 완료로 표시하지 않는다.

## 브리지 호출을 짧게 유지하기

- 변경 묶음당 계획/리뷰를 모아 보낸다. 기본은 리뷰 1회, 중요한 지적을 수정했을 때 필요한 부분만 재검토한다. 한 편지는 최대 3왕복이다.
- 전체 대화와 산출물을 보내지 않고 쟁점·diff 요약·검사 결과·읽을 경로를 준다. 경미한 상태 공유는 Issue/PR 기록으로 처리한다.
- 짧은 확인은 답변 길이와 읽을 파일 범위를 정하고, 보안/구조 검토에는 충분한 범위를 준다. 속도를 위해 검토를 생략하거나 성공 판정을 낮추지 않는다.
- 모델·추론 수준은 `scripts/ai-bridge/config.json`이 원본이다. 기본(normal)은 Codex gpt-6.1-sol·Claude claude-opus-5-5(medium), **높은 영향 등급 리뷰만 편지에 `tier: high`**를 적어 상위 설정(Claude claude-fable-5-2·high)을 쓴다. 등급을 올리는 기준은 위 리뷰 등급 표와 같다. 상주 세션 재사용은 채택하지 않았다.
- 호출 측 폴더가 더럽거나 HEAD가 검토 SHA와 다르면 스크립트가 검토 SHA의 임시 worktree에서 호출하므로, 기본 폴더에서도 호출할 수 있다. 단 검토 대상은 **커밋된 것만**이다.
- 결론 난 편지는 `node scripts/ai-bridge/archive.mjs <편지>`로 보관해 inbox에는 진행 중인 편지만 남긴다. 보관 전에 남은 쟁점은 Issue, 장기 결정은 `docs/decisions/`로 옮긴다.
