# 일반 회원 총 생성 한도 전환

- 대상: 구글 또는 이메일로 가입한 일반 회원. 인증 제공자 대신 서버 역할 클레임으로 판별한다.
- 기존 회원도 전환 이후 요청부터 `memberUsage/{uid}.count = 0`을 기준으로 차감한다. 과거 일일 사용량을 소급하지 않는다.
- 일반 회원 기본 총 한도는 5회다. 이전 전역 `config/usage.dailyLimit`과 `GEN_DAILY_LIMIT`은 계승하지 않는다.
- 기본 총 한도는 `config/usage.totalLimit`, `GEN_TOTAL_LIMIT`, 기본 5 순이다. 관리자 저장은 새 `totalLimit` 필드를 사용한다.
- 회원별 맞춤 한도는 유지한다. `limits/{uid}.totalLimit`이 없으면 해당 회원의 기존 `dailyLimit` 숫자를 계승한다.
- 총 사용량은 자정·로그아웃·한도 변경 시 초기화하지 않는다. 한도를 20에서 30으로 높이면 이미 사용한 횟수만큼 제외한 잔여 횟수만 늘어난다.
- 선점은 총 사용량과 일별 통계 문서를 하나의 트랜잭션에서 갱신한다. 실패·취소 시 같은 요청에서 1회 환불하고, 일별 통계는 예약 당시 날짜로 복구한다.
- 학생의 기존 학급 한도 및 교사·관리자의 보호용 일일 한도는 유지한다.
- `memberUsage`는 서버 전용이며 직접 문서 조회만 사용하므로 새 복합 인덱스는 필요하지 않다. 계정 삭제 시 총 사용량 문서도 삭제한다.

## 반영 순서

1. 단위·API·Firestore 규칙 테스트, 타입 검사, 린트, 빌드 확인.
2. 승인 후 커밋·푸시·병합 및 규칙/애플리케이션 배포. 운영 데이터 일괄 초기화나 과거 기록 삭제는 필요하지 않다.
3. 배포 후 맞춤 한도 없는 일반 회원 화면의 `총 사용 0/5`, 관리자 기본 총 한도 5회 표시를 확인한다. 실제 생성 검증은 별도 승인 후 실행한다.

일반 회원 총 카운터는 이 버전의 생성 요청부터 갱신된다. 이전 배포 버전으로 되돌리면 일일 한도 방식으로 돌아가므로 총 한도 정책을 유지해야 할 때는 이전 버전으로 롤백하지 않는다.
